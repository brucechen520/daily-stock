# Phase 2 — 技術指標 + 訊號引擎 + 回測方法論

## 目標

在 Phase 1 的資料基礎上，加入技術指標計算與籌碼因子，把「因子」組合成「訊號」，並且用嚴謹的回測方法驗證訊號是否真的有效，**回測站不住的規則不進入正式輸出**。

這個 phase 是整個專案技術含金量最高的部分，也是面試最容易被深挖的地方，因為「回測方法論嚴不嚴謹」直接反映開發者是不是真的懂金融資料的陷阱，還是只是套個公式跑跑看。

## 子模組拆解

### 1. `internal/indicator` — 技術指標與籌碼因子

**技術指標**（皆為公開公式，注意計算視窗要對齊實際交易日，不是自然日）：
- MA（移動平均線）：5日、20日、60日
- KD：RSV → K → D 的遞迴計算，注意第一筆資料的初始值處理（通常設 50）
- MACD：EMA12、EMA26、DIF、MACD 訊號線
- RSI：14日為主流參數

**籌碼因子**（這部分是這個專案的差異化重點，比純技術指標更少人做）：
- 外資連買/連賣天數
- 三大法人買賣超金額的 N 日移動平均（避免單日雜訊）
- 買賣超金額 / 成交量比值（衡量法人動作相對於市場熱度的強度）

```go
type Factor struct {
    Name  string
    Value float64
    // 因子計算當下所用到的資料截止時間，用於後續防止 look-ahead
    AsOfDate time.Time
}
```

### 2. `internal/signal` — 因子打分與訊號分級

簡單線性加權開始（之後可以換成更複雜的模型，但初版建議先用可解釋的規則）：

```go
type SignalScore struct {
    Symbol string
    Score  float64 // -100 ~ 100，負值偏空，正值偏多
    Factors map[string]float64 // 各因子貢獻分數，方便解釋
}
```

**訊號分級範例**：
| Score 範圍 | 分級 | 意義 |
|---|---|---|
| 60~100 | 強勢偏多 | 多項因子同時偏多 |
| 20~59 | 溫和偏多 | 部分因子偏多 |
| -19~19 | 中性 | 無明顯方向 |
| -59~-20 | 溫和偏空 | 部分因子偏空 |
| -100~-60 | 強勢偏空 | 多項因子同時偏空 |

**重要**：分數與分級只是「研究產出」，不是「買賣建議」。LLM 在 Phase 1 建立的紀律要延續——輸出時一律用「訊號研究」、「因子分析」等中性詞彙。

## 回測方法論（核心）

這部分決定整個訊號系統可不可信，逐一說明常見陷阱與對應做法。

### 陷阱 1：Look-ahead Bias（用到未來資訊）

**問題**：例如財報因子，如果用「財報所屬季度」去對應交易日，會不小心用到「還沒公布」的資訊。Q2 財報通常 8 月中才公布，但如果程式邏輯用「Q2 資料」去算 7 月的訊號，就是用了未來才存在的資訊。

**解法**：
- 每個因子都要記錄「實際公開時間」（`AsOfDate`），而不是「所屬期間」
- 回測時嚴格用「訊號產生當下，這筆資料是否已公開」做過濾
- 建議寫一個 `AssertNoLookAhead()` 檢查函式，在回測跑之前先驗證資料時間軸邏輯正確

```go
// 錯誤示範：用財報所屬季度去對應價格資料
// 正確：用財報「公布日」去對應，公布日之後才能用於當天訊號計算
if factor.PublishDate.After(signalDate) {
    return errors.New("look-ahead detected: factor published after signal date")
}
```

### 陷阱 2：Survivorship Bias（倖存者偏差）

**問題**：如果回測股票池只包含「現在還在市場上的公司」，會漏掉已下市（下市通常代表經營不善或財務問題）的公司，導致回測勝率被高估。

**解法**：
- 理想情況：用「回測當時的完整股票池」（含後來下市的公司），但這需要歷史成分股資料，免費資料源通常拿不到，這是已知限制
- 折衷做法：至少在文件中誠實揭露這個限制，並且優先選擇「大型權值股」或「上市滿一定年限」的股票池，降低下市機率對結果的扭曲程度
- 這個限制建議直接寫進 README 的 Known Limitations，不要隱藏

### 陷阱 3：Overfitting（過度擬合歷史資料）

**問題**：如果反覆調整因子權重、參數，直到歷史資料勝率好看為止，這組參數在樣本外（未來）大概率會失效，因為你等於是在「背答案」而不是「找規律」。

**解法：Walk-forward 驗證**

不要用「全部歷史資料調參 → 全部歷史資料測試」這種同一份資料訓練又測試的做法。改用滾動視窗：

```
時間軸: |----訓練期----|--測試期--|
                |----訓練期----|--測試期--|
                        |----訓練期----|--測試期--|
```

具體做法：
1. 把歷史資料切成多個滾動視窗，例如訓練期 12 個月、測試期 3 個月
2. 只用訓練期資料決定因子權重/參數
3. 用「沒看過」的測試期資料驗證勝率
4. 往前滾動視窗，重複這個過程，把每一段測試期的結果串起來看整體穩定度

**驗證指標**（不是只看單一勝率數字）：
- 各個滾動視窗的勝率是否穩定（如果第一段 70% 第二段 30%，代表規則不穩定，很可能是巧合）
- 與「隨機買進」或「持有大盤」的 baseline 比較，訊號要顯著優於隨機才有意義
- 最大回撤（Max Drawdown）：不是只看平均報酬，要看最壞情況會虧多少

```go
type BacktestResult struct {
    WindowResults []WindowResult
    OverallWinRate float64
    WinRateStdDev  float64 // 各視窗勝率的標準差，越小代表越穩定
    BaselineComparison float64 // 相對於持有大盤的超額表現
    MaxDrawdown float64
}
```

### 陷阱 4：交易成本被忽略

**問題**：回測常見錯誤是假設「買進賣出零成本」，但實際上手續費、證交稅（賣出 0.3%）會吃掉不少報酬，尤其是短線頻繁交易的規則。

**解法**：回測時內建基本交易成本假設（例如來回成本抓 0.4-0.5%），沒扣成本的勝率不能當作最終結論，只能當參考。

## 回測結果呈現原則

- 訊號只有在通過 walk-forward 驗證、且勝率穩定顯著優於 baseline 時，才進入 Phase 1 的白話摘要輸出中
- 每個訊號附帶「回測基礎」的說明，例如：「此訊號基於過去 24 個月滾動回測，平均勝率 XX%，相對於持有大盤超額 XX%」，讓使用者知道這不是憑空生成的
- **誠實揭露**：回測是歷史資料驗證，不保證未來表現，這句話要出現在每次輸出訊號的地方，不能只寫在 README 裡

## `internal/signal` 測試策略

- 用一組已知答案的假資料測試因子計算邏輯（例如手算 MA5 對答案）
- 針對 look-ahead 檢查邏輯寫專門的測試案例（故意塞入未來資料，驗證系統會擋下來）
- Walk-forward 切分邏輯要測試視窗邊界正確，不會重疊或漏掉交易日

## Phase 2 完成的定義（Definition of Done）

- [ ] MA / KD / MACD / RSI 計算完成並有單元測試驗證正確性
- [ ] 籌碼因子（連買連賣天數、N 日均買賣超）計算完成
- [ ] 因子打分與訊號分級邏輯完成
- [ ] Walk-forward 回測框架完成，可產出多視窗勝率與穩定度指標
- [ ] 回測結果附交易成本假設與 baseline 比較
- [ ] 至少一組訊號規則通過 walk-forward 驗證並記錄下來（即使勝率普通，誠實記錄也是有價值的產出）
- [ ] README / demo 附上回測結果圖表（勝率隨時間變化、與 baseline 比較）
